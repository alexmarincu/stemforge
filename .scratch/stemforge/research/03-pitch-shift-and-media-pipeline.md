# Pitch shifting & media pipeline — research report

**Ticket:** research 03 (pitch-shift engine + media pipeline)
**Status:** complete, decision-ready for the v1 stack; Windows runtime verification remains an open question
**Date:** 2026-11-14
**Scope:** local, GPL-3.0 desktop app (Linux + Windows x64) that must shift pitch by ±12 semitones with tempo preserved, preview in the NiceGUI/pywebview shell, and export WAV/FLAC/MP3. This report compares Rubber Band, `pedalboard.PitchShift`, librosa, SoundTouch, the FFmpeg `rubberband` filter, and torchaudio; then covers the FFmpeg/ffprobe binary supply chain, the canonical intermediate format, preview/export encoding, metadata, and yt-dlp 2026.10.26.

All non-measured claims link to a primary source. **[measured]** means a command run on the research host on 2026-11-14; the raw commands are in Appendix A. The host is the same one used for research 02: Intel Core i7-4800MQ (4 cores / 8 threads, Haswell, 2.7 GHz), 23 GB RAM, Linux, no GPU. Other research agents shared the same 8 vCPUs during timing runs, so wall-clock numbers are conservative; per-process CPU time is the more stable figure.

The map already settles several constraints that this report must fit:

- canonical internal audio is **32-bit float WAV**;
- preview is a **cached, webview-safe MP3**;
- exports are **WAV 24-bit, FLAC, and MP3 320**;
- pitch is **non-destructive, per-track, ±12 semitones, explicit render**, with A/B against the original;
- **no real-time pitch shifting in v1**;
- Linux target is glibc 2.35+, Windows target is 10/11 x64 with WebView2.

## TL;DR — exact recommendation

1. **Pitch engine: Rubber Band Library 4.0.0, R3 ("Finer") engine, offline mode, formant preservation on vocal material.** Invoke the CLI as `rubberband -3 -F -p <semitones> --ignore-clipping in.wav out.wav`. For a faster draft, add `--window-short`. This is the best-quality GPL-compatible option and the only one that exposes the R3 engine plus formant preservation with a practical packaging story.
2. **Do not make `pedalboard.PitchShift` the primary engine.** It does use Rubber Band [S], but it constructs the stretcher with `OptionProcessRealTime | OptionThreadingNever | OptionChannelsTogether | OptionPitchHighQuality` and never sets `OptionEngineFiner`; it therefore runs the real-time R2 engine and has no formant-preservation control. It is GPL-3.0-compatible and technically usable, but it gives up the R3/formant quality that the explicit offline render exists to deliver, and it is slower than the R2 CLI in wall time on the same machine.
3. **Do not use librosa, SoundTouch, or torchaudio for production pitch shifting.** librosa is a phase vocoder with no formant control and used **3.9 GB RSS** for a 3.5-minute stereo track [measured]; SoundTouch is extremely fast but its WSOLA/time-domain quality at ±12 semitones is a clear step down; torchaudio is in maintenance mode and uses the same phase-vocoder approach for no quality gain.
4. **Media stack: FFmpeg/ffprobe 9.0.2, GPLv3 build.** For Linux use BtbN's `ffmpeg-n9.0-latest-linux64-gpl-9.0.tar.xz` (145.6 MB archive); for Windows use gyan.dev's `ffmpeg-release-essentials.7z` (34 MB, includes librubberband) or BtbN's `ffmpeg-n9.0-latest-win64-gpl-9.0.zip` (186 MB) if you want one build source. The GPL build is required for the `rubberband` filter and is the simplest license posture for a GPL-3.0 app. The LGPL build **excludes** librubberband.
5. **Canonical intermediate: stereo 44.1 kHz, 32-bit float WAV (`pcm_f32le`), no dither, no clipping.** 4 minutes is 84.7 MB per stem. Keep it for the session; render previews as MP3 192 kbps (webview-safe, as research 01 established) and exports as WAV 24-bit / FLAC 24-bit / MP3 320 kbps.
6. **yt-dlp: use the Python API (`yt-dlp[default]`) with a bundled Deno, not the PyInstaller binary, unless you need process isolation.** The app is already Python/NiceGUI; the Python API gives structured `progress_hooks` and `postprocessor_hooks`, avoids stdout scraping, and costs a 3 MB wheel plus a 40 MB Deno wheel. Pin `yt-dlp==2026.10.26`, `yt-dlp-ejs==0.8.0`, `deno==2.9.8`. Use `format: "bestaudio/best"`, `noplaylist: True`, `outtmpl: "%(id)s.%(ext)s"`, and keep the native audio file; decode to the canonical WAV yourself. YouTube is best-effort: age-restricted content needs opt-in cookies, PO tokens cannot be generated by yt-dlp, and YouTube's ToS restricts downloading—surface this as a user-facing disclaimer.

Approximate additional bundle cost: FFmpeg 34–186 MB archive (platform-dependent), Rubber Band 1.8 MB (Windows zip) or a small Linux build, yt-dlp + Deno ≈ 43 MB. This is on top of the Demucs/torch runtime estimated in research 02.

## 2. Rubber Band Library 4.0.0

### 2.1 What it is and what it costs

Rubber Band is a C++ time-stretch/pitch-shift library plus a CLI utility. It changes tempo and pitch independently, supports offline two-pass processing and real-time streaming, and has two engines: R2 (faster, older) and R3 (finer, introduced in v3.0). The project describes R3 as producing "higher-quality results than R2 for most material, especially complex mixes, vocals and other sounds that have soft onsets and smooth pitch changes, and music with substantial bass content", at "much more CPU" ([README](https://github.com/breakfastquay/rubberband)).

Licensing ([README](https://github.com/breakfastquay/rubberband), [home](https://breakfastquay.com/rubberband/)):

- The library and CLI are **GPL-2.0-or-later**. A commercial license is available for proprietary distribution.
- For StemForge's GPL-3.0 app, **no commercial license is needed**. GPLv2-or-later code can be used under GPLv3 because GPLv3 is one of the options the "or later" clause permits ([GNU GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html#GPLCompatibility)).
- The CLI additionally uses **libsndfile (LGPL-2.1)**. The official Windows zip ships `sndfile.dll` dynamically, which is the clean LGPL arrangement. If you build a static Linux binary, you take on libsndfile LGPL relinking/source obligations; build against a shared `libsndfile.so` or ship the library and its license.

v4.0.0 adds `RubberBandLiveShifter`, a simpler pitch-only API for block-by-block use; the general `RubberBandStretcher` API is unchanged and remains binary-compatible with 1.x/2.x ([v4 announcement](https://breakfastquay.com/news/20241025.html)). For offline export, `RubberBandStretcher` is still the right API.

### 2.2 CLI vs library

| Aspect | CLI (`rubberband`) | Library (`librubberband`, C/C++) |
|---|---|---|
| Input/output | WAV via libsndfile; FLAC input also worked in the local test; output is WAV | Any container; caller supplies float buffers |
| Quality controls | `-2`/`-3`, `-F`, `--window-short`, `--pitch-hq` (RT only), many R2 tuning flags | Full option bitmask: engine, window, formant, pitch method, channels, transients, detector, phase, smoothing |
| Processing mode | Offline two-pass (`study()` + `process()`) | Offline or real-time, caller's choice |
| Progress | Prints pass/percentage lines to stderr; final throughput summary | Caller computes from `study()`/`process()` sample counts |
| Integration | Subprocess per file; temp files | In-process; no temp files; needs a C++/C bridge or cffi/pybind11 |
| Clipping | By default restarts with reduced gain if output clips; `--ignore-clipping` disables that | No automatic gain reduction; caller manages headroom |
| Packaging | Official Windows zip 1.77 MB (`rubberband.exe`, `rubberband-r3.exe`, `sndfile.dll`, `COPYING.txt`) [measured] | Build from source; GPL library link; no official Python binding |
| License | GPL-2.0-or-later + libsndfile LGPL | GPL-2.0-or-later |

**[measured]** The official Windows zip contains R2-default and R3-default executables, so Windows can invoke `rubberband-r3.exe` or pass `-3`; Linux builds can create a `rubberband-r3` symlink or pass `-3`.

**Recommendation for v1: CLI.** It is a small, official, GPL binary; it preserves float32 WAV sample format [measured]; it exposes the two-pass progress text; and it avoids writing a C++ bridge before the product exists. Put it behind a `PitchEngine` interface so a library helper can replace it later if per-file process overhead or clipping behavior becomes a problem.

### 2.3 Engines and options that matter

From the CLI help ([`rubberband --help`](https://breakfastquay.com/rubberband/usage.txt)) and the API header ([`RubberBandStretcher.h`](https://github.com/breakfastquay/rubberband/blob/default/rubberband/RubberBandStretcher.h)):

| Option | CLI | Meaning | v1 use |
|---|---|---|---|
| R2 engine | `-2` | Faster engine; default when invoked as `rubberband` | Draft/fallback |
| R3 engine | `-3` | Finer engine; default when invoked as `rubberband-r3` | **Final render** |
| Formant preservation | `-F` | Keep spectral envelope; works in R2 and R3 | On for vocals/mixes; expose toggle |
| Short window | `--window-short` | R3 "quick draft mode" | Fast draft preview |
| High-quality pitch | `--pitch-hq` | Slower pitch method **in real-time mode only** | Not relevant offline |
| Ignore clipping | `--ignore-clipping` | Do not auto-reduce gain on clipped output | **Use for stems**; manage gain later |
| Time ratio | `-t`, `-T`, `-D` | Change tempo/duration | Keep at 1 for pitch-only |
| Pitch | `-p`, `-f` | Semitones, or frequency multiplier | `-p <semitones>` |

Important nuance from the header: the `OptionPitchHighSpeed/HighQuality/HighConsistency` flags **affect only real-time mode**; in offline mode the pitch method is not adjustable. So for an offline R3 render, the quality levers are the engine, window, formant option, and channel handling—not `pitchq`.

The integration guide's "maximum quality offline pitch-shifting" recipe is `OptionProcessOffline | OptionEngineFiner | OptionChannelsTogether | OptionPitchHighQuality`, and it recommends adding `OptionFormantPreserved` for vocals/mixes to avoid the chipmunk effect ([integration notes](https://breakfastquay.com/rubberband/integration.html)). The CLI's `-3 -F` gives the R3 + formant part, but the CLI does **not** expose `OptionChannelsTogether`; its `--centre-focus` option is a different stereo treatment, not the same bit. If exact library option parity matters, a library helper is required—this is the main quality argument for the future `RubberBandLibraryEngine`.

### 2.4 Tempo and formant preservation

- **Tempo is preserved by construction** when only `-p` is used: time ratio stays 1, pitch ratio changes.
- **Formant preservation** (`-F`) keeps the spectral envelope of the original, so a +12 shift does not turn a vocal into a chipmunk. It is supported in both R2 and R3; the integration guide recommends it for vocals, acoustic recordings, speech, and mixes containing vocals. It costs CPU (measured below).
- **Range:** the project says up to three octaves is "entirely practical" ([why page](https://breakfastquay.com/rubberband/why.html)). ±12 is well inside the comfortable range.

### 2.5 Sample rate

Rubber Band is tuned for **44.1 and 48 kHz**. The integration notes say higher rates are not expected to produce detectably better output above 48 kHz, and the library supports 8–192 kHz ([integration notes](https://breakfastquay.com/rubberband/integration.html)). This supports a 44.1 kHz canonical pipeline when Demucs is in the path; do not upsample to 96 kHz for "quality".

### 2.6 Python bindings

| Option | Version / date | What it is | Fit |
|---|---|---|---|
| `pyrubberband` | 0.4.0, 2024-09-30 | ISC; subprocess wrapper around the `rubberband` CLI; writes temp WAVs; `rbargs` can pass `--fine`, `--formant` | Usable, but no progress and extra temp I/O; writing a 60-line wrapper is simpler |
| `rubberband` (PyPI) | 1.0.2 | BSD-3; a third-party simple wrapper, not the official project | Not recommended without source review |
| Official bindings | — | None | C API is stable; cffi/pybind11 possible but unnecessary for v1 |

`pyrubberband` source confirms it invokes `rubberband -q` with temp files and reads the output with `soundfile` ([source](https://github.com/bmcfee/pyrubberband/blob/main/pyrubberband/pyrb.py)). The `-q` suppresses the progress output we want, so use a direct subprocess wrapper rather than `pyrubberband` for the render path.

### 2.7 Progress output

**[measured]** Rubber Band's CLI emits progress to stderr in two passes:

```
Using R3 (finer) engine
Using time ratio 1 and frequency ratio 2
Pass 1: Studying...
0% 1% ... 99%
Calculating profile...
Pass 2: Processing...
0% 1% ... 99%
in: 441000, out: 441000, ratio: 1, ideal output: 441000, error: 0
elapsed time: 4.21102 sec, in frames/sec: 104725, out frames/sec: 104725
```

The percentages are separated by carriage returns (`\r`), so read the pipe as bytes and split on `\r`/`\n`; do not assume line-oriented text. `-q` suppresses all of it. This gives a natural progress mapping: pass 1 → 0–45%, profile → 45–50%, pass 2 → 50–100%.

### 2.8 Measured performance

210-second stereo 44.1 kHz WAV, R3 unless noted (see §8 for the full table):

| Configuration | Wall | CPU user | Peak RSS |
|---|---:|---:|---:|
| `-2 -p 12` | 33.3 s | 45.6 s | 16 MB |
| `-2 -p 12 -F` | 26.1 s | 45.8 s | 16 MB |
| `-3 -p 12` | 76.7 s | 67.5 s | 16 MB |
| `-3 -p 12 -F` | **108.8 s** | **91.0 s** | 16 MB |
| `-3 -p -12 -F` | 48.5 s | 44.7 s | 16 MB |
| `-3 --window-short -p 12 -F` | **29.7 s** | **29.3 s** | 16 MB |

R2 showed CPU time greater than wall time (multi-threaded); R3 was effectively single-threaded in these runs. R3 + formant is roughly 3.7× the wall time of the short-window draft and 1.4× the CPU of R3 without formant. The downshift was faster than the upshift on this material; do not assume symmetry. Both shifted outputs measured exactly 210.000 s, matching the input.

### 2.9 Verdict

**Use Rubber Band 4.0.0 CLI with `-3 -F` for final renders, `--window-short` for draft previews, and `--ignore-clipping` for stems.** It is the quality leader, GPL-compatible, small, and has a usable progress protocol. Its weaknesses are per-file subprocess overhead and the CLI's default auto-gain behavior; both are manageable.

## 3. `pedalboard.PitchShift` 0.9.26

### 3.1 Does it use Rubber Band?

Yes. The PyPI description states: "The `PitchShift` plugin and `time_stretch` functions use the Rubber Band Library" ([PyPI](https://pypi.org/project/pedalboard/)), and the reference says "This effect uses Chris Cannam's wonderful Rubber Band library" ([docs](https://spotify.github.io/pedalboard/reference/pedalboard.html#pedalboard.PitchShift)).

The implementation is more specific than the marketing:

```cpp
auto stretcherOptions = RubberBandStretcher::OptionProcessRealTime |
                        RubberBandStretcher::OptionThreadingNever |
                        RubberBandStretcher::OptionChannelsTogether |
                        RubberBandStretcher::OptionPitchHighQuality;
rbPtr = std::make_unique<RubberBandStretcher>(
    spec.sampleRate, spec.numChannels, stretcherOptions);
```

([`RubberbandPlugin.h`](https://github.com/spotify/pedalboard/blob/master/pedalboard/RubberbandPlugin.h))

Consequences:

- **Real-time mode**, not offline study/process.
- **R2 engine** (no `OptionEngineFiner`).
- `OptionChannelsTogether` and `OptionPitchHighQuality` are set.
- **No formant-preservation option** is exposed; the plugin's only parameter is `semitones` ([`PitchShift.h`](https://github.com/spotify/pedalboard/blob/master/pedalboard/plugins/PitchShift.h)).
- Semitone range is ±72, well beyond ±12; values outside throw `std::range_error`.

### 3.2 License and bundling

`pedalboard` is **GPL-3.0** ([LICENSE](https://github.com/spotify/pedalboard/blob/master/LICENSE)). It statically compiles JUCE 6 (GPLv3/commercial), the VST3 SDK (GPLv3), Rubber Band (GPLv2+), FFTW (GPLv2+), libmp3lame (LGPLv2, upgraded to GPLv3 for inclusion), and libgsm (ISC) ([PyPI description](https://pypi.org/project/pedalboard/)).

For a GPL-3.0 app this is license-compatible. If you freeze it into a single binary, the whole work is GPLv3; if you ship the wheel alongside the app, it remains a separate GPLv3 component. Either way, ship the license texts and a source offer for pedalboard and its bundled dependencies. There is **no GPL conflict**, but there is a real source/notice obligation.

Wheels are 3.7–5.1 MB per platform (Linux/Windows/macOS), Python 3.10–3.15, Linux glibc 2.27/2.28+, Windows x86-64 ([PyPI files](https://pypi.org/project/pedalboard/#files)).

### 3.3 Measured performance

210-second stereo, whole-array processing [measured]:

| Configuration | Wall | CPU user | Peak RSS |
|---|---:|---:|---:|
| `PitchShift(+12)` | 50.0 s | 39.3 s | 263 MB |
| `PitchShift(-12)` | 39.4 s | 34.5 s | 263 MB |

It is faster than the R3 CLI but slower than the R2 CLI in wall time on this machine; the quality is R2-real-time, not R3-offline. Memory is ~16× the CLI because the whole array and plugin buffers are in-process.

### 3.4 Verdict

**Not the primary engine for v1.** It is convenient, GPL-compatible, and one `pip install`; if StemForge ever adds a real-time pitch slider, pedalboard is a reasonable real-time preview engine (it is designed for streaming and releases the GIL). For an explicit offline render whose whole point is quality, it gives up the R3 engine and formant control for no benefit. Keep it as an optional prototype/test dependency, not a runtime dependency.

## 4. `librosa.effects.pitch_shift` 1.0.1

### 4.1 Algorithm

`librosa.effects.pitch_shift` is not a dedicated pitch shifter. It time-stretches with a phase vocoder, then resamples back to the original duration:

```python
rate = 2.0 ** (-float(n_steps) / bins_per_octave)
y_shift = core.resample(
    time_stretch(y, rate=rate, ...),
    orig_sr=float(sr) / rate,
    target_sr=sr,
    res_type=res_type,
)
```

([source](https://github.com/librosa/librosa/blob/main/librosa/effects.py))

Defaults: `n_fft=2048`, `hop_length=win_length//4`, Hann window, `res_type="soxr_hq"`, `bins_per_octave=12`. It preserves duration by construction, but has no formant preservation and no transient-aware resynthesis. At ±12 semitones the phase-vocoder artifacts (smearing, "phasiness", transient softening) are audible on music.

### 4.2 Cost and memory

**[measured]** 210-second stereo 44.1 kHz, `n_steps=+12`: **42.1 s wall, 27.0 s CPU user, 3.93 GB peak RSS**. The memory is the STFT and intermediate complex arrays, not the audio itself. Extrapolated to 4 minutes: ~48 s wall and ~4.5 GB RSS. That is unacceptable for a desktop app that is also running Demucs/torch; it would push a 16 GB machine into swapping when several stems are processed.

### 4.3 License and dependency weight

librosa is **ISC** and requires Python >= 3.12 ([PyPI](https://pypi.org/project/librosa/)). Its dependency graph includes numba/llvmlite (BSD/Apache-2.0 with LLVM exception), SciPy/NumPy (BSD), soundfile (BSD), and **soxr (LGPL-2.1-or-later)**. Those are GPL-3.0-compatible, but the LGPL `soxr` adds another relinking/notice obligation if bundled, and the install is much larger than the 5 MB wheel suggests.

### 4.4 Verdict

**Do not use for production pitch shifting.** It is fine for analysis, test fixtures, or spectrograms, but it loses on quality and memory. If a phase-vocoder fallback is ever needed, use it only on short previews and cap the input length.

## 5. SoundTouch / SoundStretch 2.3.3

### 5.1 What it is

SoundTouch is a C++ library for tempo, pitch, and playback-rate changes, with a `SoundStretch` CLI. It supports 16-bit integer and 32-bit float, mono/stereo/multichannel, real-time processing with ~100 ms latency, and is **LGPL-2.1** with a commercial non-LGPL option ([home](https://www.surina.net/soundtouch/), [download](https://www.surina.net/soundtouch/download.html)). The current official Windows binaries are 2.3.3 (2024-03-20); the local Linux build was 2.4.1.

It uses a time-domain/WSOLA-style approach rather than Rubber Band's phase-vocoder + transient/phase handling. That makes it very fast, but at large pitch shifts it tends to produce smearing and "robotic" artifacts, and it has no formant-preservation control. `soundstretch -pitch=12` preserves tempo.

### 5.2 Measured performance

**[measured]** 210-second stereo: `soundstretch -pitch=12` took **2.3 s wall / 2.0 s CPU**; `-pitch=-12` took 2.5 s / 2.1 s. That is ~90× faster than real time on this old CPU—roughly 50× faster than the R3 formant CLI.

### 5.3 Python bindings

There is **no maintained PyPI package**. `pysoundtouch` exists only as old GitHub projects (`jrising/pysoundtouch`, last push 2015; `cbrown1/pysoundtouch`, 2017) and the PyPI names `pysoundtouch`, `soundtouch`, `python-soundtouch`, etc. return 404. Using it from Python means ctypes/cffi against `libSoundTouch` or subprocess to `soundstretch`, plus LGPL dynamic-linking compliance.

### 5.4 Verdict

**Not recommended for v1.** The speed is attractive, but ±12 semitone quality is the product's core promise; SoundTouch is a clear downgrade and brings LGPL packaging work for no benefit. Keep it only as an emergency fallback if the app must run on very weak hardware.

## 6. FFmpeg's `rubberband` filter

### 6.1 GPL requirement

FFmpeg's configure lists `librubberband` in `EXTERNAL_LIBRARY_GPL_LIST`:

```
EXTERNAL_LIBRARY_GPL_LIST="
    ...
    librubberband
    ...
"
```

([`configure`](https://github.com/FFmpeg/FFmpeg/blob/master/configure))

So `--enable-librubberband` is a GPL-only build option. BtbN's GPL variant enables it; their LGPL variant explicitly disables it (`ffbuild_enabled() { [[ $VARIANT == lgpl* ]] && return -1; }` in [`50-rubberband.sh`](https://github.com/BtbN/FFmpeg-Builds/blob/master/scripts.d/50-rubberband.sh)). gyan.dev's builds include librubberband in the essentials build ([library list](https://www.gyan.dev/ffmpeg/builds/)).

### 6.2 What the filter actually runs

The filter's option table exposes `tempo`, `pitch`, `transients`, `detector`, `phase`, `window`, `smoothing`, `formant`, `pitchq`, and `channels` ([docs](https://ffmpeg.org/ffmpeg-filters.html#rubberband)). It does **not** expose an engine option. In `config_input()` it constructs the stretcher with:

```c
int opts = ... | RubberBandOptionProcessRealTime;
s->rbs = rubberband_new(inlink->sample_rate, inlink->ch_layout.nb_channels,
                        opts, 1. / s->tempo, s->pitch);
```

([`af_rubberband.c`](https://github.com/FFmpeg/FFmpeg/blob/master/libavfilter/af_rubberband.c))

Therefore:

- It always runs **real-time mode**.
- With no `OptionEngineFiner`, it runs the default **R2 engine**.
- `pitchq=quality` sets `OptionPitchHighQuality`, which is a real-time pitch method, **not** the R3 engine.
- `formant=preserved` is available and maps to `OptionFormantPreserved`.
- `pitch` and `tempo` are **scale factors**, not semitones/percent: +12 semitones = `pitch=2.0`; -12 = `pitch=0.5`.

So the FFmpeg filter is a convenient R2-real-time pitch shifter, not a replacement for `rubberband -3`.

### 6.3 Measured performance

**[measured]** 210-second stereo:

| Configuration | Wall | CPU user |
|---|---:|---:|
| `rubberband=pitch=2.0` | 23.5 s | 20.2 s |
| `rubberband=pitch=2.0:pitchq=quality:formant=preserved` | 77.6 s | 61.1 s |

It is faster than the R3 CLI and comparable to the R2 CLI, as expected. The quality+formant variant is close to R3-formant CPU but still lacks R3.

Progress is easy: `-nostats -progress pipe:1` emits `out_time_us`, `speed=…x`, `progress=continue/end` [measured]. Since pitch shifting preserves duration, `out_time_us / duration_us` is a valid progress fraction.

### 6.4 Verdict

**Fallback/preview only.** It is already in the FFmpeg binary, so it can render a quick preview without spawning Rubber Band, and it is useful if the Rubber Band binary is missing. For final export, the R3 CLI is better. If you use it, pass `pitchq=quality:formant=preserved:channels=together` and accept R2 quality.

## 7. torchaudio 2.11.1

`torchaudio.functional.pitch_shift` is a phase-vocoder pitch shifter with an STFT and resampling step; it takes `n_steps`, `bins_per_octave`, `n_fft`, `win_length`, `hop_length`, and `window` ([docs](https://docs.pytorch.org/audio/stable/generated/torchaudio.functional.pitch_shift.html)). It preserves duration, has no formant control, and shares librosa's phase-vocoder artifacts.

Two practical blockers:

1. **Maintenance mode.** The project says it has "transitioned TorchAudio into a maintenance phase"; features were deprecated in 2.8 and removed in 2.9; its focus is ML data processing, not general signal processing ([README](https://github.com/pytorch/audio)).
2. **No quality advantage, and a large extra dependency.** `torchaudio 2.11.1` requires `torch>=2.11` ([PyPI](https://pypi.org/project/torchaudio/)), which the Demucs stack's `torch 2.15` satisfies—so there is no version conflict, but there is also no reason to add another audio package. Its `pitch_shift` is still a phase vocoder with the same artifacts as librosa and no formant control. If torch is already present for Demucs, the incremental wheel may be modest, but the quality story does not improve.

License is BSD-2-Clause, so it is GPL-compatible. **Do not use it for pitch shifting.**

### 8.3 What this means for a 4-stem session

- **Four stems, R3 + formant:** ~104 s CPU per 4-minute stem → ~416 s CPU total. On four free cores, ideal wall time is ~104 s; on this 2013 CPU expect ~2–3 minutes with I/O and scheduling. On a current 6–8 core desktop, roughly 1–2 minutes.
- **Four stems, R3 draft:** ~34 s CPU per stem → ~134 s CPU total; ~35–60 s wall on four cores.
- **Four stems, R2:** ~52 s CPU per stem → ~208 s CPU total; R2 can use multiple threads, so do not run four R2 jobs at once without limiting concurrency.
- **Four stems, SoundTouch:** ~9 s CPU total; quality is the trade-off.
- **Memory:** Rubber Band ~16 MB; FFmpeg moderate; pedalboard ~263 MB; librosa ~3.9 GB. The last is a hard no for a desktop app that also loads torch.

The product does not need to render all stems at once: only tracks whose semitone value changed. Cache the original stems and render lazily. That keeps the common case to one or two stems.

## 9. Recommended pitch design and progress strategy

### 9.1 Exact v1 behavior

- Per-track semitone value `n ∈ [-12, +12]`, float allowed (e.g., +3.5).
- Explicit **Render** action; no real-time slider. On render, run Rubber Band R3 offline with formant preservation on the selected stem(s).
- Keep the original stem untouched; write `shifted.wav` as float32 WAV at the same sample rate/channel count; generate `shifted.mp3` preview; keep `original.mp3` for A/B.
- Default formant preservation **on**. Expose "Preserve formants" as an advanced toggle; turning it off is faster (108.8 s → 76.7 s on the test) but risks chipmunk artifacts on vocals.
- Offer a **Draft** toggle that uses `--window-short` (108.8 s → 29.7 s on the test) and clearly labels it as lower quality. Do not silently use draft for export.
- Use `--ignore-clipping` and keep float32 headroom. Do not let the CLI auto-reduce gain independently per stem; that would change the mix balance. Apply a single shared gain/limiter at preview/export if needed.

### 9.2 Commands

Final render:

```bash
rubberband -3 -F -p "$SEMITONES" --ignore-clipping \
  "$CANONICAL_STEM.wav" "$SHIFTED_STEM.wav"
```

Draft:

```bash
rubberband -3 --window-short -F -p "$SEMITONES" --ignore-clipping \
  "$CANONICAL_STEM.wav" "$SHIFTED_STEM.wav"
```

Fallback if the R3 binary is unavailable:

```bash
rubberband -2 -p "$SEMITONES" --ignore-clipping \
  "$CANONICAL_STEM.wav" "$SHIFTED_STEM.wav"
```

After render, verify with ffprobe that duration is within one sample-block of the input, sample rate/channels match, and the file is readable. Reject/re-render on mismatch.

### 9.3 Progress mapping

Use the CLI's two passes:

| Phase | Fraction |
|---|---:|
| Process start / decode already done | 0–2% |
| Pass 1 "Studying" | 2–45% |
| "Calculating profile" | 45–50% |
| Pass 2 "Processing" | 50–98% |
| Output validation + MP3 preview encode | 98–100% |

For multiple stems, overall = `(completed_stems + current_fraction) / total_stems`. Parse `\r`-delimited percentages; use the final `elapsed time` line to compute throughput and a smoothed ETA. If the process exits without a final percentage, mark the render failed rather than snapping to 100%.

Alternative if you later use the library: offline mode calls `study()` then `process()`; progress is `studied_samples/total` and `processed_samples/total` ([integration notes](https://breakfastquay.com/rubberband/integration.html)). This avoids text parsing and gives exact block-level progress.

For FFmpeg's filter fallback, use `-nostats -progress pipe:1` and `out_time_us / duration_us`; `out_time_ms` is also microseconds in FFmpeg's progress output [measured], so use `out_time_us` explicitly.

### 9.4 Cancellation and failure handling

- Run each render as a subprocess in its own process group; on cancel, terminate the group, wait up to 5 s, then kill.
- Write to a temp path (`.partial.wav`) and atomically rename on success; delete partials on failure/cancel.
- Cache completed renders; a cancel discards only the in-flight stem.
- If the process fails, surface stderr's last lines; common causes are missing `sndfile.dll` on Windows and unwritable temp dirs.
- Never trust the output filename alone; validate with ffprobe (codec, sample rate, channels, duration).

### 9.5 Why not pitch before separation?

Pitch-shift **after** separation. Demucs is trained on original-pitch audio; shifting before separation can degrade the separation and changes all stems together, which conflicts with the per-track pitch model. Separate first, cache the original stems, then render pitch per stem. This also makes A/B trivial: the original stems are untouched. The artifacts remain independent—re-running separation does not require re-running pitch, and re-pitching does not require re-separating—but the recommended order is separation → pitch.

## 12. Canonical intermediate format and media pipeline

### 12.1 Canonical format

**Stereo 44.1 kHz, 32-bit float WAV (`pcm_f32le`).** This matches the map's standing decision and research 02's Demucs output rate. Rationale:

- Rubber Band processes float samples internally, and its CLI **preserves** float32 WAV input as float32 output [measured]; no conversion loss.
- Float32 gives headroom for pitch-shift overshoot and per-stem summing; 16-bit does not.
- 44.1 kHz is one of Rubber Band's tuned rates ([integration notes](https://breakfastquay.com/rubberband/integration.html)) and Demucs' native output rate (research 02).
- WAV is universally decodable by FFmpeg and libsndfile; no codec licensing issue.
- 4 minutes stereo f32 = `44100 × 4 × 2 × 240 = 84,672,000` bytes ≈ **84.7 MB** per stem. Four stems ≈ **339 MB**. Budget for it.
- Use `-rf64 auto` if a session can exceed 4 GB; a 4-minute stem will not, but a long DJ mix might.

Do **not** use 16-bit WAV as the intermediate: pitch shifting can produce inter-sample peaks and the quantization/dither decisions get baked in too early. Do **not** use FLAC as the working format: FFmpeg's FLAC encoder supports only integer `s16`/`s32`, not float; 24-bit FLAC is a good archive/export format but requires a conversion and loses float headroom. Do **not** use MP3/AAC/Opus as an intermediate; decode once from the source and keep PCM.

Canonicalization command (adjust `-ac`/`-ar` by policy):

```bash
ffmpeg -v error -y -i "$INPUT" -map 0:a:0 -vn -sn -dn \
  -af "aresample=resampler=soxr:precision=28" \
  -ac 2 -ar 44100 -c:a pcm_f32le -rf64 auto \
  "$CANONICAL.wav"
```

`resampler=soxr` requires an FFmpeg built with libsoxr (BtbN GPL and gyan full do; gyan essentials does not—use plain `-ar 44100` there). If the source is already 44.1 kHz stereo, skip `-ar`/`-ac`/`aresample` and just decode to `pcm_f32le`. If the source is 48 kHz and Demucs is in the path, let Demucs resample to 44.1 kHz rather than resampling twice. **Open question:** whether to force 44.1 kHz for the pitch-only path or preserve 48 kHz; see §15.

### 12.2 Preview transcode

The map's shell is NiceGUI + pywebview; research 01 found **MP3 is the least fragile codec in both WebKitGTK and WebView2**, provided `gst-plugins-good` is present on Linux. Do not switch preview to Opus just because it is technically better; the webview is the constraint.

- Preview: **MP3 192 kbps CBR**, 44.1 kHz, stereo, `-id3v2_version 3` for Windows Explorer compatibility, `-map_metadata 0`.
- Why not 320 kbps preview: 192 kbps is transparent enough for A/B at typical desktop levels and halves the cache/bandwidth; export is where 320 matters.
- Why not WAV preview: a 4-minute WAV is 84 MB and the webview's range requests would move a lot of bytes; MP3 is ~5.8 MB at 192 kbps for 4 minutes.
- Why not Opus: WebKitGTK's Opus support depends on GStreamer plugins and WebView2's codec set; MP3 is the safer lowest common denominator. (Opus remains a good choice for a future native audio engine.)
- Generate previews after pitch render, from the shifted float32 WAV, not from the source.
- Use `app.add_media_files()` / the local HTTP route as research 01 recommends; do not use `file://`.

```bash
ffmpeg -v error -y -i "$SHIFTED.wav" -map_metadata 0 \
  -c:a libmp3lame -b:a 192k -id3v2_version 3 \
  "$SHIFTED.mp3"
```

**[measured]** MP3 encode (VBR q2) of a 210 s track took ~6 s wall / ~5 s CPU on this host; Opus 128k took ~5.8 s; FLAC 24 took ~2.1 s; WAV 24 took ~0.4 s. Preview encode is not the bottleneck.

### 12.3 Export encoders

| Format | FFmpeg encoder | Recommended settings | Notes |
|---|---|---|---|
| WAV 24-bit | `pcm_s24le` | `-c:a pcm_s24le`; optionally `-rf64 auto` | Universal; largest; no dither needed from f32→24-bit |
| FLAC 24-bit | `flac` (native) | `-c:a flac -sample_fmt s32 -bits_per_raw_sample 24 -compression_level 8` | Lossless, ~1/4 the size of WAV on the test signal; tags/pictures supported |
| MP3 320 | `libmp3lame` | `-c:a libmp3lame -b:a 320k -id3v2_version 3` | Compatibility; CBR 320 for predictable size; LAME LGPL |
| WAV 16-bit (optional) | `pcm_s16le` | `-c:a pcm_s16le` + dither | Only if the user asks; dither from f32 |

`ffmpeg -h encoder=flac` confirms the native encoder supports `s16`/`s32` only, not float [measured]. `ffmpeg -h muxer=mp3` confirms `-id3v2_version` supports 3 and 4, default 4; use 3 for Windows Explorer compatibility [measured].

Do **not** use `libfdk_aac` (nonfree, not in GPL builds) or add AAC to v1; the map's export set is WAV/FLAC/MP3.

Example export:

```bash
# FLAC 24
ffmpeg -v error -y -i "$SHIFTED.wav" -map_metadata 0 \
  -c:a flac -sample_fmt s32 -bits_per_raw_sample 24 -compression_level 8 \
  -metadata title="$TITLE" -metadata artist="$ARTIST" \
  "$OUT.flac"

# MP3 320
ffmpeg -v error -y -i "$SHIFTED.wav" -map_metadata 0 \
  -c:a libmp3lame -b:a 320k -id3v2_version 3 \
  -metadata title="$TITLE" -metadata artist="$ARTIST" \
  "$OUT.mp3"

# WAV 24
ffmpeg -v error -y -i "$SHIFTED.wav" -map_metadata 0 \
  -c:a pcm_s24le -metadata title="$TITLE" -metadata artist="$ARTIST" \
  "$OUT.wav"
```

|---|---|---|
| MP3 | title, artist, album, date, genre, comment | Yes, PNG stream (`attached_pic`) |
| FLAC | title, artist, album, date, genre | Yes, PNG picture block |
| WAV | title, artist, album, date, genre; comment not written | No standard cover |
| M4A | title, artist only in the quick test | Yes, `attached_pic` |
| Opus | title, artist on the stream; album missing | Embedding via FFmpeg's Ogg muxer failed |

Practical rules:

- Use MP3 or FLAC when rich tags and cover art matter; they are the map's primary formats.
- For MP3 cover art: `-c:v copy -disposition:v attached_pic -id3v2_version 3`; the cover is a video stream with `attached_pic=1`.
- For FLAC cover art: same `attached_pic` pattern; the native FLAC muxer writes a picture block.
- For WAV: accept limited `LIST/INFO` tags; do not promise cover art.
- For Opus: if preview/export is ever added, verify tag placement with `ffprobe -show_streams`; do not assume `format_tags` contains everything.
- Store the source URL in `comment`/`purl` where supported; it is useful for attribution and debugging.
- yt-dlp's `FFmpegMetadata` can fill tags from the info dict, but the app should treat its own metadata as authoritative and only use yt-dlp's values as defaults. `EmbedThumbnail` needs `mutagen` (in `yt-dlp[default]`) and is optional.

### 12.5 Cache layout and keys

```
<cache>/sources/<source_id>/native.<ext>       # untouched download
<cache>/sources/<source_id>/canonical.wav      # f32 44.1k stereo
<cache>/sources/<source_id>/original.mp3       # preview for A/B
<cache>/sources/<source_id>/stems/<stem>.wav   # separation output, f32
<cache>/renders/<render_key>/<stem>.wav        # pitch-shifted f32
<cache>/renders/<render_key>/<stem>.mp3        # preview
<cache>/yt-dlp/                                # yt-dlp's own cache
```

`render_key = blake2b(source_hash | stem | semitones | formant | window_mode | engine_version | sample_rate | channels)`. Store a JSON sidecar with engine/version/options and validation results. Use LRU eviction with a disk cap; a 4-stem session is ~340 MB before previews, so a 5–10 GB cap is reasonable for a desktop app. This is a **cache**, not the project library: it may be evicted, and the session must be able to rebuild it from the source.

### 12.6 Full progress model

| Stage | Weight | Source of progress |
|---|---:|---|
| Download (optional) | 0–35% | yt-dlp `progress_hooks` (bytes) |
| Decode/canonicalize | 35–42% | FFmpeg `-progress` or indeterminate (fast) |
| Pitch pass 1 (study) | 42–65% | Rubber Band CLI `Pass 1` percentages |
| Pitch profile | 65–68% | "Calculating profile..." |
| Pitch pass 2 | 68–92% | Rubber Band CLI `Pass 2` percentages |
| Preview MP3 | 92–97% | FFmpeg `-progress` |
| Validate/commit | 97–100% | ffprobe + atomic rename |

For multiple stems, collapse the pitch stages into a per-stem fraction and aggregate. Emit a heartbeat at least every 1–2 s so the UI can distinguish "working" from "hung"; the CLI prints percentages frequently, so this is easy.

ydl_opts = {

### 13.3 Audio-only format selection

Use:

```python
"format": "bestaudio/best",
"noplaylist": True,
```

- `bestaudio` selects the best audio-only format; `best` is a fallback for sites that do not mark audio-only formats.
- Do **not** use `bestvideo+bestaudio`; downloading video is wasted bandwidth and may trigger merges.
- YouTube's best audio is typically Opus (~160 kbps) in WebM or AAC (~128 kbps) in M4A. Since the app decodes to canonical WAV, choose the best available stream rather than forcing a container. If you want to prefer Opus explicitly, `bestaudio[acodec=opus]/bestaudio/best` is valid, but it can reduce availability; `bestaudio/best` is the safer default.
- Keep `noplaylist: True` unless the user explicitly imports a playlist; a watch URL with a list parameter should not silently download the whole list.
- For metadata-only inspection, `extract_info(url, download=False)`; then validate `duration`, `age_limit`, and `formats` before downloading.
- Reject live streams (`is_live`) and excessively long tracks in v1.

A complete starting options dict:

```python
ydl_opts = {
    "format": "bestaudio/best",
    "noplaylist": True,
    "outtmpl": {"default": "%(id)s.%(ext)s"},
    "paths": {"home": str(source_cache)},
    "cachedir": str(ytdlp_cache),
    "windowsfilenames": True,
    "trim_file_name": 120,
    "quiet": True,
    "no_warnings": True,
    "js_runtimes": {"deno": {"path": str(bundled_deno)}},
    "progress_hooks": [on_progress],
    "postprocessor_hooks": [on_postprocessor],
    "logger": logger,
}
```

### 13.4 Postprocessing

For the canonical pipeline, **do not** use `FFmpegExtractAudio` to convert to WAV. Download the native bestaudio file, keep it in the source cache, and decode it yourself with the canonical FFmpeg command. This preserves the original for re-renders and avoids a second lossy/format conversion decision.

If you do use a postprocessor, the relevant ones are:

| Postprocessor | Key | Use |
|---|---|---|
| Extract audio | `FFmpegExtractAudio` | Convert to `wav`/`flac`/`mp3`; can delete the original |
| Metadata | `FFmpegMetadata` | Copy title/artist/date/description into tags |
| Thumbnail | `EmbedThumbnail` | Embed cover art; requires `mutagen` (in `[default]`) |

`FFmpegExtractAudio`'s `preferredcodec` supports `mp3`, `aac`, `m4a`, `opus`, `vorbis`, `flac`, `alac`, `wav` ([source](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/postprocessor/ffmpeg.py)). If used, `preferredcodec: "wav"` decodes once to PCM; `preferredcodec: "best"` leaves a common audio format alone. For StemForge, direct decode is clearer and keeps the native file.

`FFmpegMetadata` uses the info dict to fill common tags and can attach chapters; `EmbedThumbnail` handles MP3, FLAC, M4A/MP4, MKV/MKA, and Ogg/Opus (the latter via mutagen) ([source](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/postprocessor/embedthumbnail.py)). Treat these as convenience, not the source of truth.

### 13.5 Progress hooks

`progress_hooks` receive a dict with:

- `status`: `"downloading"`, `"error"`, or `"finished"`;
- `info_dict`;
- `filename`, `tmpfilename`;
- `downloaded_bytes`, `total_bytes`, `total_bytes_estimate`;
- `elapsed`, `eta`, `speed`;
- `fragment_index`, `fragment_count`.

`postprocessor_hooks` receive `status` (`"started"`, `"processing"`, `"finished"`), `postprocessor`, and `info_dict` ([YoutubeDL docstring](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/YoutubeDL.py)). Hooks are guaranteed to be called at least once with `"finished"` on success, and at least `"started"` + `"finished"` for postprocessors.

For a UI, map download bytes to 0–80% of the import stage and postprocessor events to 80–100%; the actual decode/canonicalization is a separate stage after download. If using the binary, use `--newline --progress-delta 0.5 --progress-template` and `--print after_move:filepath`; the README explicitly recommends these structured outputs over parsing normal stdout ([README](https://github.com/yt-dlp/yt-dlp#embedding-examples)).

### 13.6 Caching

- `cachedir` controls yt-dlp's own cache (player JS, nsig, client configs). The README's default is `${XDG_CACHE_HOME}/yt-dlp` (Linux); set it explicitly to the app cache on both platforms and expose "Clear YouTube cache". `False` disables it; `--rm-cache-dir` deletes it.
- Do **not** rely on yt-dlp's cache for media. Keep the downloaded native file under `<cache>/sources/<source_id>/native.<ext>`.
- Deduplicate by YouTube video ID (`info["id"]`); re-download only if the file is missing/corrupt.
- Validate cached media with ffprobe (duration, codec, sample rate, channels) and a content hash before reuse.
- Cache the canonical WAV and each pitch render separately; pitch changes should never re-download or re-decode.
- A 4-minute source at native Opus/AAC is ~5–10 MB; the canonical WAV is ~85 MB; four stems ~340 MB. Set an LRU cap.

### 13.7 Age, cookies, PO tokens, and rate limits

These are the practical limits as of 2026-11-14; YouTube changes frequently.

**Age restriction.** `age_limit` is a *filter*, not a bypass: "An integer representing the user's age in years. Unsuitable videos for the given age are skipped" ([YoutubeDL docstring](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/YoutubeDL.py)). Age-restricted videos require account cookies; `web_embedded` is added as a fallback for age-restricted videos but "only successfully works around the age-restriction sometimes" ([README extractor args](https://github.com/yt-dlp/yt-dlp#youtube)).

**Cookies.** `--cookies FILE` or `--cookies-from-browser BROWSER[+KEYRING][:PROFILE][::CONTAINER]`; supported browsers are brave, chrome, chromium, edge, firefox, opera, safari, vivaldi, whale; Linux keyrings are basictext, gnomekeyring, kwallet, kwallet5, kwallet6 ([README](https://github.com/yt-dlp/yt-dlp#authentication-options)). The Python API equivalents are `cookiefile` (path or stream) and `cookiesfrombrowser` (tuple of browser, profile, keyring, container) ([docstring](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/YoutubeDL.py)). Caveats:

- Using an account risks temporary or permanent ban; yt-dlp's wiki advises restraint and a throwaway account where possible.
- YouTube rotates account cookies on open browser tabs; the wiki documents a private-window export procedure.
- OAuth login no longer works; use cookies.
- Cookies grant account access: never log them, never upload them, store them only with explicit opt-in, and delete temporary cookie files after use.

**PO tokens.** YouTube is enforcing Proof of Origin tokens for some clients. yt-dlp cannot generate them; they must come from a provider plugin or `po_token` extractor args. The wiki's current enforcement table (last edited 2026-07-12) ([PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide)):

| Client | PO Token required for | Notes |
|---|---|---|
| `web` | Subs, GVS | Only SABR formats |
| `web_safari` | GVS* | HLS; *no GVS token at this time |
| `mweb` | GVS | Recommended with a provider |
| `tv` | Not required | All formats DRM'd if cookies aren't passed; only SABR in some cases |
| `tv_simply` | GVS | No account cookies |
| `web_embedded` | Not required | Only embeddable videos |
| `web_music` | GVS | |
| `web_creator` | GVS | Requires account cookies |
| `android` | GVS or Player | No account cookies |
| `android_vr` | Not required | No made-for-kids videos |
| `ios` | GVS or Player | No account cookies |

Default YouTube clients are `tv_samsung,visionos,web`; if no JS runtime is available, `web` and `tv_samsung` are omitted. With logged-in cookies the defaults change (`tv_samsung,web_embedded,web` for free accounts; `web_creator,tv_samsung,web` for premium). PO tokens are bound to the video ID, have a limited lifespan (possibly as short as 12 hours), and must be refreshed. A PO token provider plugin (e.g. `bgutil-ytdlp-pot-provider`) is the recommended workaround, but it adds a service/plugin and is outside v1 scope ([PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide)).

**JS runtime.** YouTube needs an external JavaScript runtime to solve JS challenges; yt-dlp uses `yt-dlp-ejs` scripts and Deno by default. The official PyInstaller/zipimport binaries bundle the EJS scripts but **not** the runtime; you must still ship Deno. Without a JS runtime, some clients/formats are unavailable ([EJS wiki](https://github.com/yt-dlp/yt-dlp/wiki/EJS)).

**Rate limits.** The wiki reports ~300 videos/hour for guest sessions (~1000 webpage/player requests/hour) and ~2000 videos/hour for accounts (~4000 requests/hour), and recommends 5–10 s between downloads to avoid "This content isn't available, try again later" ([Extractors wiki](https://github.com/yt-dlp/yt-dlp/wiki/Extractors#youtube)). For a desktop app, enforce a per-session download limit and backoff; do not retry aggressively.

**v1 posture:** support public, non-age-restricted videos by default; offer opt-in browser cookies for age-restricted/private content; do not bundle a PO token provider; show a clear error with a link to the PO Token Guide when YouTube refuses. This keeps the app local and avoids shipping an arms-race component.

### 13.8 Filename sanitization

The safest rule: **never use the video title as a path component.** Use the YouTube ID (or an app-generated UUID) for storage, and keep the title in metadata/display names.

If a title-based filename is needed (e.g. user-facing export), use yt-dlp's sanitizer semantics:

- `sanitize_filename(s, restricted=False)` replaces the characters `"`, `*`, `:`, `<`, `>`, `?`, `|`, `/`, and `\` with full-width Unicode lookalikes, strips control characters, turns `?` into nothing, `:` into ` -`, and path separators into `_`. Example [measured]: `AC/DC: "Back in Black" <Live> | 1979? *bonus*\track` → `AC⧸DC： ＂Back in Black＂ ＜Live＞ ｜ 1979？ ＊bonus＊⧹track`.
- `restricted=True` transliterates to ASCII and collapses punctuation: same input → `AC_DC_-_Back_in_Black_Live_1979_bonus_track`.
- `is_id=True` preserves an ID unchanged; IDs are safe by construction.
- `sanitize_path(..., force=True)` handles `..` traversal and Windows-invalid characters; example [measured]: `music/../evil:name?.mp3` → `evil#name#.mp3`.

For StemForge:

- Use `outtmpl: "%(id)s.%(ext)s"` and store under a per-source directory.
- Set `windowsfilenames: True` so a file created on Linux remains usable on Windows/exFAT; set `trim_file_name` to e.g. 120.
- Prefer `restrictfilenames: False` for Unicode display names, but still pass through `sanitize_filename`; if maximum portability matters, use `True`.
- Reject/normalize Windows reserved names (`CON`, `PRN`, `AUX`, `NUL`, `COM1`…`COM9`, `LPT1`…`LPT9`) yourself; do not assume the sanitizer handles them.
- Normalize Unicode to NFC and enforce a total path length below 240 characters.
- After computing the final path, assert it is under the cache root (defense in depth against template injection/path traversal).

### 13.9 Legal / ToS

YouTube's Terms of Service say users may not "access, reproduce, download, distribute, transmit, broadcast, display, sell, license, alter, modify or otherwise use any part of the Service or any Content" except as specifically permitted, with prior written permission, or as permitted by law; automated access is also restricted ([YouTube Terms](https://www.youtube.com/t/terms)). Downloading audio may also infringe copyright.

StemForge should:

- show a first-use disclaimer that the user is responsible for having the rights to the content and for complying with YouTube's terms;
- not present YouTube import as a licensed feature or a substitute for purchasing music;
- keep the feature opt-in and local (no proxying, no account pooling, no telemetry); YouTube import is the **only** network path in the app, so make it explicit and disable-able;
- document that age-restricted/private content requires the user's own cookies and that using an account carries a ban risk.

This is product/legal guidance, not legal advice; get counsel before shipping if YouTube import is a headline feature.

## 15. Open questions

1. **Canonical sample rate:** force 44.1 kHz everywhere (simplest, matches Demucs) or preserve 48 kHz for pitch-only sessions and resample only when separating? Forcing 44.1 costs one high-quality resample on 48 kHz sources; preserving 48 avoids it but complicates stem alignment. Recommendation: force 44.1 for v1, revisit if users notice.
2. **Formant default:** always on, or on only for vocals/instrumental? It costs ~35% more CPU (R3 91.0 s vs 67.5 s on the test). Recommendation: default on, expose a toggle.
3. **Draft mode:** should the UI expose `--window-short` as a "fast preview" render, or keep only one render quality? Draft is 3.7× faster; users may accept it for auditioning. Recommendation: expose it behind an "Advanced/Quality" control, never as the default export.
4. **Clipping/gain policy:** `--ignore-clipping` preserves level but can leave float samples >1.0; exporting to 24-bit then clips. Do we apply a shared limiter across stems, per-stem normalization, or leave headroom and warn? This affects mix balance and is a product decision.
5. **Rubber Band CLI vs library helper:** is per-stem subprocess overhead acceptable for 4 stems, or should v1 build a small C++/cffi helper for exact progress, no temp files, and `OptionChannelsTogether`? The CLI exposes R3 + formant but not channels-together; a helper is the only way to get exact library option parity. Recommendation: CLI for v1, measure; the interface leaves room.
6. **FFmpeg build size:** ship the 145.6 MB BtbN GPL archive, the 34 MB gyan Windows build, or invest in a custom minimal audio-only GPLv3 build? The custom build is the only way to get near a 250 MB installer without dropping rubberband.
7. **FFmpeg provenance:** mirror the exact BtbN/gyan archive into StemForge releases (best for reproducibility/GPL source offer), or fetch at build time from upstream (smaller repo, supply-chain risk)? Recommendation: mirror and record SHA256.
8. **yt-dlp packaging:** Python API + Deno (recommended) vs official binary + Deno. The binary adds ~40 MB but isolates crashes and simplifies EJS bundling. Which failure mode matters more?
9. **yt-dlp update strategy:** yt-dlp breaks when YouTube changes; the README calls stable releases "often stale" and recommends nightly for regular users. A pinned 2026.10.26 will eventually fail. Does v1 ship a manual "update yt-dlp" path (out of scope per map) or accept breakage until an app update?
10. **PO tokens:** do we ship a PO token provider plugin/service (complex, ToS-sensitive) or accept that some videos fail with a clear error? Recommendation: fail clearly in v1.
11. **Age-restricted content:** support opt-in browser cookies, or exclude age-restricted videos entirely? Cookies increase support burden and account-ban risk.
12. **YouTube legal review:** the ToS restricts downloading; does the product need a stronger disclaimer, a rights attestation, or a decision to defer YouTube import? This is the largest non-technical risk.
13. **Preview bitrate:** 192 kbps vs 256 kbps vs 320 kbps for MP3 preview; 192 is recommended for size, but A/B on good speakers may favor 256.
14. **Loudness normalization:** none, ReplayGain-style tags, or EBU R128 at export? Pitch shifting can change perceived loudness slightly; a shared normalization policy would keep A/B fair.
15. **Metadata scope:** which tags are first-class (title/artist/album/date/genre/comment/source URL/cover), and do we embed covers in MP3/FLAC by default? Cover embedding adds encode time and size but is expected by users.
16. **Windows runtime verification:** all Rubber Band/FFmpeg/Deno measurements here are Linux; verify the Windows `sndfile.dll`, `rubberband.exe`/`rubberband-r3.exe`, gyan FFmpeg, and WebView2 MP3 path on a real Windows 10/11 VM.
17. **Code signing:** bundled `ffmpeg.exe`, `rubberband.exe`, `deno.exe`, and the installer need signing to avoid SmartScreen warnings; who owns the certificate and CI signing step?
18. **Rubber Band 4.x future:** v4.0.0 is from 2024; if a 4.1/5.0 lands, does the CLI/progress contract change? Pin 4.0.0 and add a smoke test; upgrade deliberately.
19. **`soxr`/LGPL:** if librosa is ever shipped for analysis, its `soxr` dependency adds LGPL obligations; confirm whether it is dynamically linked.
20. **A/B loudness matching:** should the shifted preview be loudness-matched to the original for fair comparison, or left untouched to expose the pitch algorithm's level changes?

## Appendix A — measured commands

Host: Intel i7-4800MQ (4C/8T, 2.7 GHz), 23 GB RAM, Linux; other research jobs ran concurrently. Tools: `rubberband 4.0.0`, `ffmpeg 9.0.2`, `soundstretch 2.4.1`, `pedalboard 0.9.26`, `librosa 1.0.1`, `yt-dlp 2026.10.26`.

Test signal: 210 s, 44.1 kHz, stereo, 16-bit WAV, pink noise + 220 Hz sine (`ffmpeg -f lavfi -i anoisesrc ... -f lavfi -i sine=... -filter_complex amix ...`). It is synthetic; real music may differ, especially on transient-heavy material.

```bash
# Rubber Band CLI cases
rubberband -2 -p 12 test210.wav out_r2.wav
rubberband -2 -p 12 -F test210.wav out_r2_f.wav
rubberband -3 -p 12 test210.wav out_r3.wav
rubberband -3 -p 12 -F test210.wav out_r3_f.wav
rubberband -3 -p -12 -F test210.wav out_r3_m12_f.wav
rubberband -3 --window-short -p 12 -F test210.wav out_r3_draft.wav

# FFmpeg filter cases
ffmpeg -y -i test210.wav -af rubberband=pitch=2.0 -c:a pcm_f32le out_ff.wav
ffmpeg -y -i test210.wav -af rubberband=pitch=2.0:pitchq=quality:formant=preserved \
  -c:a pcm_f32le out_ff_qf.wav

# SoundTouch
soundstretch test210.wav out_st.wav -pitch=12
soundstretch test210.wav out_st_m.wav -pitch=-12

# pedalboard (venv with pedalboard 0.9.26)
python - <<'PY'
from pedalboard import PitchShift
from pedalboard.io import AudioFile
with AudioFile('test210.wav') as f:
    audio, sr = f.read(f.frames), f.samplerate
out = PitchShift(semitones=12)(audio, sr)
PY

# librosa (venv with librosa 1.0.1)
python - <<'PY'
import librosa
y, sr = librosa.load('test210.wav', sr=None, mono=False)
y2 = librosa.effects.pitch_shift(y, sr=sr, n_steps=12)
PY

# encode benchmarks
ffmpeg -y -i test210.wav -c:a libopus -b:a 128k -vbr on -application audio preview.opus
ffmpeg -y -i test210.wav -c:a libmp3lame -q:a 2 export.mp3
ffmpeg -y -i test210.wav -c:a flac -sample_fmt s32 -bits_per_raw_sample 24 \
  -compression_level 8 export.flac
ffmpeg -y -i test210.wav -c:a pcm_s24le export.wav

# progress probe
ffmpeg -nostats -progress pipe:1 -y -i short10.wav -af rubberband=pitch=2.0 \
  -c:a pcm_f32le /tmp/out.wav
```

`ffprobe` was used to verify codec, sample format, sample rate, channels, duration, and tags:

```bash
ffprobe -v error -show_entries stream=codec_name,sample_fmt,sample_rate,channels \
  -show_entries format=duration,size,bit_rate -of default=nw=1 file
ffprobe -v error -show_entries format_tags -of json file
```

The metadata test used a 300×300 PNG cover and wrote MP3/FLAC/WAV/M4A/Opus with title/artist/album/date/genre/comment; results are summarized in §12.4. The Opus cover attempt failed with "Could not write header (incorrect codec parameters ?): Invalid argument"; that is an FFmpeg Ogg muxer limitation in this version, not a codec limitation of Opus itself.
